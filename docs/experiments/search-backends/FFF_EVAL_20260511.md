# FFF Search Backend Evaluation

This note records the initial source inspection for `dmtrKovalenko/fff` as a possible Packet28 search backend or optional MCP peer.

## Source Snapshot

- Repository: `https://github.com/dmtrKovalenko/fff`
- Revision inspected: `39f67c0cf97c22a71408fc6de2f2888c5c4a700e`
- Local inspection path: `/tmp/fff-eval`
- Evidence used: `README.md`, `Cargo.toml`, `crates/fff-core/Cargo.toml`, `crates/fff-core/src/lib.rs`, `crates/fff-grep/src/lib.rs`, `crates/fff-mcp/Cargo.toml`, `crates/fff-mcp/src/server.rs`

## Useful Capabilities

- Long-lived Rust file finder with one repository scan reused across repeated searches.
- Content grep modes for plain text, regex, and fuzzy matching.
- Typo-resistant fuzzy path and content matching.
- Frecency and query-history ranking backed by local storage.
- Git-aware result annotations for modified, staged, untracked, and ignored files.
- Background watcher and warm in-memory file/cache model.
- MCP server exposing agent-facing search tools.

## Packet28 Fit

`fff` is a strong candidate for replacing or augmenting parts of Packet28's custom `p28` search engine, especially fuzzy matching, frecency, git-aware ranking, and warm repeated-search performance.

It is not a blind drop-in replacement for current Packet28 search because Packet28 also owns:

- reducer packet shape and compact preview semantics
- raw artifact recovery and fetch handles
- fallback reasons and route/provenance reporting
- daemon index status and setup/doctor evidence
- real-repo parity artifacts under `docs/experiments/`
- local-first storage expectations under Packet28 paths and schemas
- the current Rust 1.75 / edition 2021 build contract; current `fff` sources use edition 2024, and crates.io currently advertises a nightly-tagged `fff-search` package, so direct linking needs an MSRV/build-policy decision

## Recommended Adapter Plan

1. Add an experimental backend enum such as `p28 --engine fff` only after the dependency/MSRV story is explicit.
2. Build a thin adapter that converts `fff` results into Packet28 `SearchResult` packets without changing public `p28` output, or launch `fff-mcp` as an optional peer if direct linking would break the release build.
3. Preserve current fallback fields, token estimates, path filtering, raw recovery handles, and compact output.
4. Run the real-repo suite with both backends and compare indexed hit rate, elapsed time, output token count, fallback count, memory use, and correctness against native `rg`.
5. Adopt `fff` only if the adapter improves repeated-search behavior without weakening Packet28's artifact and parity contracts.

## Adapter Smoke

Packet28 now has an opt-in `p28 --engine fff` path that launches an external `fff-mcp` process, calls its MCP `grep` tool, and converts the returned text into the existing Packet28 `SearchResult` shape with `engine=fff_mcp`. Packet28 also uses `fff-mcp` from `p28 --engine auto` when the indexed planner would otherwise fall back to broad/common legacy grep and `fff-mcp` is available. Selective indexed search remains the default exact path.

Local verification on 2026-05-11:

- `cargo test -p packet28-search-cli p28_fff_engine_adapts_mcp_grep_results`
- `cargo test -p packet28-search-cli p28_auto_uses_fff_for_broad_index_fallback_when_available`
- `cargo test -p packet28-search-cli`
- `cargo check -p packet28-search-cli`
- built upstream `fff-mcp` from `39f67c0` with `cargo build -p fff-mcp --no-default-features --release` because the default `zlob` feature requires Zig locally
- real adapter smoke: `P28_FFF_MCP_BIN=/tmp/fff-eval/target/release/fff-mcp target/debug/p28 SearchResult --engine fff --stats --max-total-matches 5`
- `docs/experiments/run_p28_search_backend_comparison.sh` runs repeated native `rg`, default `p28`, and opt-in `p28 --engine fff` comparisons.
- `docs/experiments/search-backends/FFF_COMPARE_20260511/summary.md` and `results.jsonl` record 81 rows: 27 native `rg`, 27 default `p28`, and 27 `p28 --engine fff` rows across Packet28, ripgrep, and fd with three repeats each for `fn`, `Result`, and `TODO`.

Observed real adapter smoke output reported `transport=inproc backend=fff_mcp matches=5 files=1 returned=5`. This proves the MCP bridge and Packet28-shaped output path work, but it is not yet enough to make `fff` the default or claim search superiority.

The repeated comparison had 0 failed rows. The opt-in `fff` adapter returned `backend=fff_mcp` for 27/27 rows. Default `p28` returned `indexed_regex` for 15/27 rows and intentionally fell back to `legacy_rg` for 12/27 broad/common-literal rows. `fff` was strong on compact output size for broad queries, but the comparison is still search-backend evidence only; it does not prove raw recovery, daemon integration, artifact fetch, or whole-agent parity.

## Current Decision

Do not replace Packet28 search wholesale. Keep the fixed Packet28 indexed path for selective exact queries, use `fff-mcp` for broad/common auto fallbacks when available, keep explicit `--engine fff`, and evaluate deeper adoption with the same real-repo evidence gate.
